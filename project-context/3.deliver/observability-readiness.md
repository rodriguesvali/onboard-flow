## 1. Purpose

This document defines the Delivery readiness position for operating and observing the OnboardFlow AI MVP.

The default operating path remains deterministic, provider-free, and inexpensive. Live CrewAI/Gemini execution and CrewAI AMP tracing are intentionally gated because they require credentials, operator action, and cost awareness.

## 2. Current Observability Surface

Available now:

- Backend health check: `GET /health`.
- Startup log with active Flow mode and app tracing flag:

```text
onboardflow_backend_started flow_mode=<deterministic|crewai> crewai_amp_tracing=<true|false>
```

- Application logs correlated by `run_id` for generation, validation, Flow execution, normalization, refinement, and simulated dispatch.
- Deterministic agent-operation logs for document, IT, training, communication, and refinement steps.
- Live CrewAI event logs for Crew kickoff, task, and agent start/completion/failure events.
- Run status API exposes persisted result, revision history, action history, and dispatch receipts.
- Simulated dispatch receipts record channel, recipient, task title, status, preview payload, and timestamp.

Not available yet:

- Centralized log aggregation.
- Metrics endpoint.
- Distributed tracing outside CrewAI AMP.
- Alerting or SLO dashboards.
- Browser automation proving the full approve-and-dispatch click path.

These gaps are acceptable for the MVP local/demo Delivery target.

## 3. Default Deterministic Observability

Use this profile for local demos, QA, and default CI:

```text
ONBOARDFLOW_FLOW_MODE=deterministic
CREWAI_AMP_TRACING=false
```

Expected behavior:

- No real Gemini or other provider call is made.
- No CrewAI AMP trace is published.
- Logs still include `run_id` for generate, refine, and dispatch operations.
- Simulated email and service desk tools create persisted receipts without external calls.

Minimum local checks:

```text
curl http://127.0.0.1:8000/health
```

Generate an onboarding plan, refine it if needed, then dispatch it. Confirm:

- Backend logs include the same `run_id` across lifecycle events.
- `GET /api/onboarding/runs/{runId}` returns `status=done`.
- Dispatch receipts are persisted after `POST /api/onboarding/runs/{runId}/dispatch`.
- Frontend shows receipt statuses as `Enviado` or `Ja enviado`.

## 4. CrewAI AMP Tracing Gate

CrewAI documentation confirms:

- `crewai login` authenticates the local environment with CrewAI AMP.
- `crewai traces enable` enables trace collection preference.
- `crewai traces status` reports trace collection status.
- A code-level `Crew(tracing=True|False)` flag controls tracing for a Crew execution and has higher priority than environment variables or local user preferences.
- CrewAI also documents the native `CREWAI_TRACING_ENABLED` environment variable, but OnboardFlow does not use it as the application setting.

OnboardFlow application rule:

```text
CREWAI_AMP_TRACING=<true|false>
```

This app-specific variable maps to the explicit `Crew(tracing=...)` argument for live CrewAI generation and refinement. Keep it `false` by default.

## 5. Manual Live Provider Smoke

Run this only after explicit operator approval.

Prerequisites:

- `GEMINI_API_KEY` available in the operator environment.
- CrewAI AMP account access if tracing will be verified.
- No real secrets committed to the repository, logs, screenshots, or artifacts.

Commands:

```text
cd backend
uv sync --all-extras --dev
uv run crewai login
uv run crewai traces enable
uv run crewai traces status
export ONBOARDFLOW_FLOW_MODE=crewai
export CREWAI_AMP_TRACING=true
export GEMINI_API_KEY=<secret-from-operator-environment>
uv run uvicorn onboardflow.api.main:app --app-dir src --host 127.0.0.1 --port 8000
```

Then generate or refine one onboarding plan. Startup alone is not enough because traces are published only when live CrewAI execution reaches `Crew.kickoff()`.

Acceptance:

- Backend startup log shows `flow_mode=crewai crewai_amp_tracing=True`.
- One generate or refine operation completes with `status=done`.
- Logs show Crew, task, and agent lifecycle entries correlated to the `run_id`.
- CrewAI AMP displays the trace for that execution.
- The response remains normalized by the backend Flow before persistence or frontend display.

## 6. Failure Handling

If live provider execution fails:

- Capture `run_id`, operation, timestamp, and high-level error message.
- Do not paste provider keys, raw secret values, or private AMP session data into artifacts.
- Re-run with `CREWAI_AMP_TRACING=false` if the goal is to isolate provider execution from tracing setup.
- Fall back to `ONBOARDFLOW_FLOW_MODE=deterministic` for demos and CI.

If deterministic dispatch visibility fails:

- Check that the run reached `status=done` before dispatch.
- Call `GET /api/onboarding/runs/{runId}` and confirm `dispatchReceipts`.
- Re-dispatch the same run and confirm idempotent `Ja enviado` behavior instead of duplicate external calls.

## 7. CI Boundary

Default CI must continue to use:

```text
ONBOARDFLOW_FLOW_MODE=deterministic
CREWAI_AMP_TRACING=false
```

Default CI must not require:

```text
GEMINI_API_KEY
CREWAI_API_KEY
CREWAI AMP login/session credentials
email provider credentials
service desk credentials
```

A live provider workflow may be added later only as a separate manual `workflow_dispatch` gate after Agentic Architect approval.

## 9. Acceptance Criteria

This readiness artifact is accepted when the Agentic Architect confirms:

- Deterministic logs, health check, run status, and dispatch receipts are enough for default Delivery readiness.
- CrewAI AMP tracing remains opt-in and manual.
- `CREWAI_AMP_TRACING` stays the OnboardFlow application flag for explicit `Crew(tracing=...)`.
- Native `CREWAI_TRACING_ENABLED` is documented as CrewAI-owned, not as the OnboardFlow app setting.
- Live CrewAI/Gemini validation remains outside default CI.
