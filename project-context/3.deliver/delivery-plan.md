## Recommended Approach

Use an incremental Delivery path.

### Stage 1: Local Demo Readiness

Goal: make the approved MVP easy to run and validate locally without provider spend.

Deliverables:

- `project-context/3.deliver/local-ops.md`
- Corrected backend `.env.example`
- Documented deterministic startup commands
- Documented smoke checks for `/health`, Angular route, generate, refine, and dispatch

Default runtime:

```text
ONBOARDFLOW_FLOW_MODE=deterministic
CREWAI_AMP_TRACING=false
```

Live CrewAI/Gemini remains opt-in only.

### Stage 2: Fast CI Readiness

Goal: catch normal breakages on every PR without real LLM calls.

Recommended default CI checks:

```text
cd backend && uv sync --all-extras --dev
cd backend && uv run alembic upgrade head
cd backend && uv run pytest
cd backend && uv run python -m compileall src tests
cd frontend && npm ci
cd frontend && npm test -- --watch=false
cd frontend && npm run build
cd frontend && npx prettier --check .
```

CI must set:

```text
ONBOARDFLOW_FLOW_MODE=deterministic
CREWAI_AMP_TRACING=false
```

CI must not require:

```text
GEMINI_API_KEY
CREWAI_API_KEY
CREWAI_AMP login
real LLM calls
```

Deliverable:

- `project-context/3.deliver/ci-plan.md`

Implementation of `.github/workflows/ci.yml` should happen only after the CI plan review gate is approved.

### Stage 3: Container And Preview Readiness

Goal: make local/demo execution reproducible outside the current IDE.

Recommended first step:

- Keep the existing Dev Container as the primary reproducible development environment.
- Add Docker Compose only for app runtime once local ops and CI are approved.
- Do not add PostgreSQL, Redis, Kubernetes, ECS, queues, or managed cloud services for the MVP demo.

Candidate future deliverables:

- Backend Dockerfile
- Frontend static build container or static-hosting notes
- `docker-compose.yml` for backend + frontend demo

### Stage 4: Live Provider And Observability Gate

Goal: intentionally validate live CrewAI/Gemini behavior and CrewAI AMP traces without making that the default.

Live validation should require explicit operator action:

```text
uv run crewai login
uv run crewai traces enable
uv run crewai traces status
ONBOARDFLOW_FLOW_MODE=crewai
CREWAI_AMP_TRACING=true
GEMINI_API_KEY=<secret>
```

Acceptance should include:

- One successful live generate or refine.
- Trace visible in AMP.
- No secret values committed.
- Logs include `run_id`, flow mode, and agent/task lifecycle entries.

## Risks

- `backend/.env.example` has a stale tracing variable and may confuse operators.
- Frontend API base URL is compile-time/static, so deployed preview environments will need an explicit configuration strategy.
- SQLite is acceptable for MVP/local demo but not enough for concurrent production use.
- Live CrewAI/Gemini behavior is intentionally outside default CI and can drift if not periodically validated through a gated workflow.
- No browser automation currently proves the full click path for `Aprovar e simular envios`.
- No GitHub Actions pipeline currently protects the repository from regressions.
