## 1. MVP Architecture Philosophy and Principles

### MVP Design Principles

1. Plan-first value: the MVP must prove that OnboardFlow AI can turn new-hire data into a complete, reviewable onboarding plan.
2. Human approval by design: generated content is draft output until reviewed by HR.
3. Structured output over free-form chat: the primary experience is a workbench with forms, sections, checklists, messages, risks, and history.
4. Grounded agent behavior: agents use local catalogs, schemas, and explicit task boundaries.
5. Traceability from day one: every generation run records input, agent activity, validation results, and output summaries.
6. Integration-light MVP: external systems are deferred; exportable artifacts prove value before automation risk is introduced.

### Core vs Future Feature Decision Framework

MVP core:

- Manual and JSON employee intake.
- Required field validation.
- CrewAI orchestration with the six PRD-defined agents.
- Local catalogs for documents, access, equipment, training, and message templates.
- Consolidated onboarding plan in structured JSON and Markdown.
- Basic web workbench for review.
- Action/history log.

Future:

- Editable plan workbench with generated-vs-human diff.
- Configurable catalogs and catalog versioning.
- Status tracking across onboarding lifecycle.
- HRIS, ITSM, IAM, LMS, email, chat, and document integrations.
- SSO/RBAC, managed persistence, analytics, and governance reports.

### Technical Architecture Decisions

#### ADR-001: Web-first MVP workbench

Decision: Build a lightweight web workbench as the primary MVP interface.

Rationale: The PRD identifies HR users as the primary users and requires an operational, compact, reviewable experience. A web workbench supports form intake, visible agent progress, structured plan review, and export better than a CLI-only flow.

Implications:

- The initial UI will prioritize the intake-to-plan path.
- CLI/API usage can exist for development and QA but is not the primary user experience.

#### ADR-002: Angular and PrimeNG frontend

Decision: Use Angular with PrimeNG for the frontend workbench.

Rationale: The PRD requires a lightweight, responsive web workbench, and `project-context/1.define/mantadory-tools.md` records PrimeNG as a mandatory frontend tool. Angular with PrimeNG supports the required form, table, status, tab, and review surfaces while aligning the architecture with the Build-phase tooling constraint.

Implications:

- Frontend implementation should use TypeScript.
- API requests should call a backend API owned by the Python service or a thin backend boundary.
- The architecture remains compatible with local development and future hosted deployment.

#### ADR-003: Python CrewAI backend service

Decision: Implement agent orchestration in a Python backend service using CrewAI.

Rationale: CrewAI is the approved runtime in the PRD. Python is the natural execution environment for CrewAI and keeps agent configuration, schemas, and tool adapters close to the orchestration layer.

Implications:

- The frontend should not call LLM providers directly.
- The backend owns validation, catalogs, agent execution, output normalization, and history logging.

#### ADR-004: DDD with Hexagonal Architecture backend

Decision: Structure the backend as a composition of Domain-Driven Design (DDD) and Hexagonal Architecture (Ports and Adapters).

Rationale: OnboardFlow AI has a clear onboarding domain with entities, workflows, policies, generated plans, run history, and future external integrations. DDD keeps the core business language and rules explicit, while Hexagonal Architecture protects that domain from framework, storage, LLM provider, CrewAI, and future HRIS/ITSM/IAM adapter details.

Implications:

- Domain models, value objects, and domain services must not depend on FastAPI, CrewAI, databases, or LLM SDKs.
- Application services orchestrate use cases such as generating an onboarding plan and retrieving run status.
- Ports define required capabilities such as catalog access, run-history persistence, LLM/agent execution, Markdown rendering, and future external-system actions.
- Adapters implement those ports for local JSON/YAML catalogs, SQLite/file storage, CrewAI, API routes, and future integrations.
- Framework code remains at the edge of the backend and translates requests/responses into application commands and DTOs.

#### ADR-005: Local persistence and catalogs for MVP

Decision: Use local JSON/YAML catalogs and lightweight local persistence for MVP.

Rationale: The PRD explicitly permits local JSON/YAML or database-backed catalogs and file-based or embedded persistence. External integrations are out of scope.

Implications:

- Catalogs should be versionable in the repository.
- Generated plans and run histories can be stored locally in development.
- If SQLite is used, database schema changes must still be managed through Alembic migrations.
- Future managed-database choices should preserve the same migration discipline without changing domain logic.

#### ADR-006: Streaming or progress updates as nice-to-have MVP behavior

Decision: The UI should expose generation progress where feasible, but the MVP architecture must still work with polling or request/response.

Rationale: The PRD says agent execution should expose progress where feasible. It does not require true token streaming.

Implications:

- Initial implementation may use a job status endpoint.
- Real-time streaming can be added later without changing core domain contracts.

## 5. Multi-Agent System Specification

### Crew Composition

The MVP uses the six PRD-defined agents:

1. Onboarding Coordinator Agent.
2. HR Intake Agent.
3. Compliance Agent.
4. IT Provisioning Agent.
5. Training Agent.
6. Communication Agent.

This exceeds the generic template suggestion of three to four agents because the approved PRD explicitly defines six core agents and maps them to the MVP scope.

### Collaboration Pattern

Recommended process: coordinator-led sequential orchestration with parallelizable specialist tasks after intake validation.

Baseline execution:

1. Validate raw input with deterministic validation.
2. HR Intake Agent creates employee profile and missing-data summary.
3. Coordinator prepares shared case context.
4. Compliance, IT Provisioning, and Training agents run from the shared context and catalogs.
5. Communication Agent drafts messages using employee profile and specialist outputs.
6. Coordinator generates the initial agenda, executive summary, and next recommended actions.
7. Coordinator consolidates all outputs into the final plan.
8. Output Normalizer validates the final schema and renders Markdown.
9. Action History Logger records run metadata and summaries.

### Task Dependency Model

| Task | Depends on | Output |
| --- | --- | --- |
| Validate input | Raw employee data | Validation result |
| Build profile | Validation result and raw employee data | Employee profile |
| Generate document checklist | Employee profile and document catalog | Required documents and risks |
| Generate IT checklist | Employee profile, access catalog, equipment catalog | IT tasks and critical first-day items |
| Generate training path | Employee profile and training catalog | Training path |
| Generate communication drafts | Employee profile and specialist outputs | Draft messages |
| Generate initial agenda | Employee profile, start date, and specialist outputs | Initial agenda |
| Consolidate final plan | All specialist outputs | Final onboarding plan |
| Log run history | All task results | Action/history log |

### Agent Output Contracts

All agent outputs must be parseable as structured JSON before consolidation.

Required common fields:

- `agentName`
- `status`
- `summary`
- `items`
- `pendingActions`
- `risks`
- `assumptions`

The final plan must include:

- `employeeProfile`
- `validation`
- `executiveSummary`
- `requiredDocuments`
- `itChecklist`
- `trainingPath`
- `initialAgenda`
- `communications`
- `pendingActions`
- `riskFlags`
- `status`
- `nextRecommendedActions`
- `actionHistory`

### Error Handling

- If validation fails, generation can continue only in draft mode and must mark missing fields as pending.
- If a specialist agent fails, the final plan must include an incomplete-section marker.
- If output schema validation fails, retry once with a schema-repair prompt or deterministic repair step.
- If retry fails, preserve partial results and return an error summary.
- No error path may silently omit agent activity from the run history.

### Performance Targets

- Required field validation: under 2 seconds.
- Standard MVP plan generation: under 120 seconds.
- UI must remain responsive while generation runs.
- Agent run metadata must capture latency and token usage where available.

## 7. Backend Architecture Specification

### Architectural Style

The backend must combine DDD with Hexagonal Architecture (Ports and Adapters).

DDD responsibilities:

- Keep onboarding concepts explicit in the domain layer: employee input, onboarding run, agent action, onboarding plan, catalog item, status, pending action, risk flag, and communication draft.
- Place business rules and invariants in domain services, value objects, or policies rather than API route handlers or adapter code.
- Use application services to coordinate use cases without leaking framework or provider concerns into the domain.

Hexagonal responsibilities:

- Define ports for catalog reads, run history persistence, agent orchestration, LLM/model access, Markdown rendering, and future external integrations.
- Implement adapters for CrewAI, local JSON/YAML catalogs, SQLite or file persistence, generated Markdown, and API transport.
- Keep FastAPI or equivalent HTTP handlers as inbound adapters that translate requests into application commands and return response DTOs.
- Keep outbound adapters replaceable so post-MVP integrations can be added without rewriting domain logic.

### API Routes

#### `POST /api/onboarding/generate`

Purpose: submit employee data and start plan generation.

Request:

- Employee input fields defined in PRD.
- Optional mode: manual form or JSON.

Response options:

- Synchronous response with complete plan for short runs.
- Or `runId` plus status endpoint for longer runs.

#### `GET /api/onboarding/runs/{runId}`

Purpose: retrieve run status, partial progress, final output, or error details.

Response:

- Run status.
- Agent activity summaries.
- Validation result.
- Final plan when complete.
- Error summary when failed.

### Python Service Interface

Recommended endpoints or callable boundary:

- `POST /generate-onboarding-plan`
- `GET /runs/{run_id}`

The service must:

- Own CrewAI execution.
- Own catalog loading.
- Own LLM provider configuration.
- Return structured JSON.
- Generate Markdown representation.

### Validation Strategy

Use schemas at three boundaries:

1. Frontend input validation for immediate user feedback.
2. API validation before backend orchestration.
3. Python schema validation for agent outputs and final plan.

Recommended schema technologies:

- TypeScript schemas for frontend/API request validation.
- Pydantic models for Python service contracts.

### Database Versioning

Database schema changes must be versioned with Alembic.

Rules:

- Alembic migration files are the source of truth for database schema evolution.
- MVP SQLite schemas must be created and evolved through Alembic rather than ad hoc `create_all` or manual SQL changes.
- Migration scripts belong in the infrastructure/database area and must not leak persistence concerns into the domain or application layers.
- Migrations should be runnable in local development, CI, and future hosted environments.

### Persistence Strategy

MVP acceptable options:

- File-based storage under a local data directory.
- SQLite for runs, plans, and action history.

Recommended for implementation:

- Start with SQLite if the web workbench needs repeatable run retrieval.
- Keep catalogs as repository-versioned JSON/YAML files.

Future:

- Managed relational database if hosted persistence is required.
- Managed object storage only if generated artifacts need external retention.

## 9. Data Flow and Runtime View

### Primary Plan Generation Flow

```text
1. HR user submits employee input.
2. Frontend validates basic field shape.
3. Frontend calls the backend API.
4. Python API validates request shape and creates OnboardingRun.
5. Deterministic validator checks required fields and formats.
6. HR Intake Agent synthesizes profile and missing-data summary.
7. Coordinator constructs shared case context.
8. Compliance Agent produces document/compliance output.
9. IT Provisioning Agent produces access/equipment output.
10. Training Agent produces training path output.
11. Communication Agent drafts stakeholder messages.
12. Coordinator consolidates final plan.
13. Output Normalizer validates final plan schema.
14. History Logger persists run and agent summaries.
15. API returns plan JSON and Markdown.
16. Workbench renders the plan for human review.
```

### Correspondence Rules

- Every visible final-plan section must map to at least one specialist output or deterministic validation result.
- Every specialist output must have a matching `AgentAction`.
- Every risk flag must appear in `pendingActions`, `riskFlags`, or both.
- Every communication draft must be labeled as draft/requires review.
- Every recommendation should be traceable to employee input, local catalog, or explicit agent assumption.

## 11. Security and Compliance Architecture

### Security Requirements

- Keep LLM and service credentials server-side only.
- Validate all input at frontend, API, and backend boundaries.
- Treat user-provided job descriptions, policy text, or notes as untrusted input.
- Do not store sensitive documents in MVP.
- Avoid raw PII in debug logs.
- Require human approval before any future external action.

### Compliance Boundaries

The MVP must not:

- Score employees.
- Rank candidates or employees.
- Recommend hiring, firing, promotion, demotion, disciplinary action, or compensation.
- Automatically provision access.
- Automatically send communications.

### Audit Requirements

The system must record:

- Run creation timestamp.
- Submitted input snapshot.
- Validation result.
- Agent name and action type.
- Result summary.
- Errors and retries.
- Final plan generation status.

## 13. Testing and Quality Assurance Specifications

### Testing Strategy

Unit tests:

- Input validation.
- Catalog matching.
- Schema validation.
- Markdown rendering.
- Status calculation.

Integration tests:

- Full generation flow with mocked LLM/CrewAI outputs.
- Specialist failure with partial plan.
- Missing required fields draft-mode flow.
- Export JSON/Markdown consistency.

End-to-end tests:

- Complete remote software engineer scenario.
- Missing manager or invalid start date scenario.
- Hybrid sales representative scenario.
- On-site operations employee scenario.
- Compliance-heavy finance or HR scenario.

### Quality Gates

- At least 90% of P0 acceptance criteria pass before MVP completion.
- 100% of required input fields are validated.
- Generated plan includes all required sections for complete input.
- Missing-data scenario produces explicit pending actions.
- No generated message is presented as sent or approved.
- Agent action history exists for each generation run.

## 15. Risks and Mitigations

| Risk | Level | Architectural mitigation |
| --- | --- | --- |
| Agent hallucination | High | Local catalogs, typed schemas, output validation, human review |
| Sensitive employee data exposure | High | Data minimization, no document storage, server-side secrets, restricted logs |
| Unsafe autonomy | High | No live provisioning or sending in MVP, future approval gates |
| Long-running agent requests | Medium | Run status endpoint and optional job-based execution |
| Low trust in recommendations | Medium | Rationale fields, source categories, assumptions, visible agent activity |
| Scope creep into HRIS replacement | Medium | Explicit MVP boundary and future integration section |
