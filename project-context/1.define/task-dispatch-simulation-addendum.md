## 1. Business Request

Before moving to Deliver, OnboardFlow AI must close the onboarding workflow after plan review by emulating that every actionable task in the generated onboarding plan was sent to the proper recipient.

The MVP still must not send real emails, create real service desk tickets, provision access, enroll training, or call external systems. The new requirement is a simulated dispatch layer with explicit tools per dispatch channel and auditable receipts proving that the system would have sent each task.

## 2. Scope Decision

This is a Define addendum, not Deliver planning.

The business request changes the approved MVP scope and must be reviewed as a PRD/SAD addendum before backend, frontend, integration, or QA implementation resumes.

It changes the MVP completion point from:

- Generate and review a complete onboarding plan.

To:

- Generate, review, approve, simulate dispatch of all actionable tasks, and show dispatch receipts.

## 3. MVP Requirements Addendum

### PRD-P0-010: Simulated Task Dispatch

User story: As an HR user, I want each approved onboarding task to be routed through the correct simulated tool so that I can demonstrate an end-to-end onboarding flow without integrating real external systems.

Acceptance criteria:

- The user can trigger simulated dispatch only after a generated plan exists.
- The dispatch operation covers every actionable item in the approved plan, including documents, IT checklist items, training items, initial agenda items, communication drafts, pending actions, risks that require follow-up, and next recommended actions where applicable.
- Each dispatch record includes task title, source plan section, owner or audience, channel, simulated tool name, simulated destination, status, timestamp, and generated receipt id.
- Email-style tasks are handled by a dedicated simulated email tool.
- Service-desk-style tasks are handled by a dedicated simulated service desk tool.
- No real email, service desk, ITSM, IAM, LMS, chat, HRIS, or provisioning API is called.
- Dispatch results are persisted in the run history and returned to the frontend.
- The frontend clearly shows that dispatch was simulated.
- Re-running dispatch must be idempotent for the same plan revision: already-dispatched tasks should return their existing simulated receipts or be marked as already simulated, not duplicated silently.

## 4. Dispatch Tool Model

### SimulatedEmailDispatchTool

Purpose: Emulate sending review-approved communication or follow-up tasks by email.

Primary task types:

- Welcome communication to collaborator.
- Manager preparation communication.
- HR follow-up for documents, pending actions, risks, and plan review notes.
- Training reminders when owner or audience is collaborator, HR, or manager.
- Initial agenda notifications.

Output: simulated receipt with `channel=email`, `toolName=SimulatedEmailDispatchTool`, `recipient`, `subject`, `status=sent_simulated`, and `simulated=true`.

### SimulatedServiceDeskDispatchTool

Purpose: Emulate opening operational requests in a service desk queue.

Primary task types:

- IT access requests.
- Equipment requests.
- Account setup requests.
- AI tool access or license requests when present in IT checklist, pending actions, or special access notes.
- Any task whose owner is TI or whose channel is explicitly classified as service desk.

Output: simulated receipt with `channel=service_desk`, `toolName=SimulatedServiceDeskDispatchTool`, `destinationQueue`, `ticketKey`, `status=sent_simulated`, and `simulated=true`.

### AI Tools Fit

AI tools fit the process as an onboarding task category, not as a separate real integration in the MVP.

Routing rule:

- If the plan includes access to AI tools, licenses, model workbenches, coding assistants, or approved AI platforms, the task is dispatched through `SimulatedServiceDeskDispatchTool`.
- If the plan includes AI usage policy, responsible AI training, or manager guidance about AI tools, the task is dispatched through `SimulatedEmailDispatchTool`.

Future production can introduce a real `AIToolProvisioningTool`, but that is out of MVP scope.

## 5. Routing Rules

Default routing:

| Source section | Default channel | Recipient or destination |
| --- | --- | --- |
| `communications` audience `collaborator` | Email | collaborator email |
| `communications` audience `manager` | Email | direct manager |
| `communications` audience `hr` | Email | mock HR user |
| `communications` audience `it` | Service desk | IT onboarding queue |
| `requiredDocuments` | Email | collaborator and HR |
| `itChecklist` | Service desk | IT onboarding queue |
| `trainingPath` | Email | collaborator, manager, or HR based on owner |
| `initialAgenda` | Email | collaborator and manager |
| `pendingActions` owner `TI` | Service desk | IT onboarding queue |
| `pendingActions` owner other than `TI` | Email | owner role recipient alias |
| `riskFlags` requiring action | Email | HR |
| `nextRecommendedActions` | Email | HR |

The backend owns routing. The frontend must not decide dispatch channel by itself.

## 6. Architecture Addendum

Add a post-plan Dispatch use case to the backend application layer:

- `DispatchOnboardingTasksUseCase`
- `DispatchRouter`
- `DispatchToolPort`
- `SimulatedEmailDispatchTool`
- `SimulatedServiceDeskDispatchTool`
- `DispatchReceiptRepository` behavior through the existing run persistence boundary

The Flow remains responsible for generation and refinement. Dispatch is a deterministic post-generation application workflow, not an LLM task and not an autonomous Crew action.

The dispatch layer must:

- Read the current run and plan revision.
- Derive dispatchable tasks from the final structured plan.
- Route each task to a simulated tool.
- Persist receipts and append action-history entries.
- Return a dispatch summary to the frontend.

## 7. API Addendum

Add:

```text
POST /api/onboarding/runs/{runId}/dispatch
```

Purpose: approve the current plan revision for simulated task dispatch and return dispatch receipts.

Response fields:

- `runId`
- `revisionNumber`
- `status`
- `simulated`
- `dispatchSummary`
- `receipts`
- `agentActivity`

Recommended statuses:

- `sent_simulated`
- `already_sent_simulated`
- `failed_simulated`

## 9. Frontend Addendum

Replace the current session-local `Aprovar plano` behavior with a backend-backed action:

- Button label: `Aprovar e simular envios`
- Disabled while dispatch is running.
- Success state shows receipt counts by channel.
- Results view shows simulated receipts in a compact section.
- Copy must make clear that no external system was called.

## 10. QA Addendum

Validation must cover:

- Dispatch cannot run for an unknown run.
- Dispatch cannot run before a generated plan exists.
- Complete sample plan produces receipts for all actionable sections.
- IT tasks route to service desk.
- Communication drafts and collaborator/manager tasks route to email.
- AI tool access routes to service desk when present.
- AI tool policy/training guidance routes to email when present.
- Re-dispatch for the same revision is idempotent.
- Receipts persist and appear in run status.
- No real network call or external integration is invoked.

## 11. Deferred

- Real email sending.
- Real ITSM/service desk ticket creation.
- Real IAM, LMS, HRIS, chat, or AI tooling provisioning.
- Approval workflow with real authentication/RBAC.
- Delivery-stage production deployment and secret management.
