## 1. Purpose

Define the minimal frontend workflow for the OnboardFlow AI critical path: Generate Onboarding Plan.

This specification translates the approved PRD and SAD into a small Angular/PrimeNG implementation target. It intentionally uses mocked frontend services so the UI can be implemented and validated before backend integration.

## 4. Route and Screen Model

Use one route:

```text
/onboarding/generate
```

The route hosts a single feature container that switches between two views:

1. Form view: visible in `idle`, `running`, and `error`.
2. Results view: visible in `done`.

The results view is a page-level view inside the same route, not a second route. This keeps navigation minimal while satisfying the workflow need for a distinct review surface after generation.

## 5. User Workflow

1. HR user opens `/onboarding/generate`.
2. UI shows the employee onboarding form and an idle status banner.
3. HR user may choose `Claro` or `Escuro` for the visual theme.
4. HR user fills required fields.
5. HR user selects `Gerar plano`.
6. UI enters `running`, disables form actions that could corrupt the run, and shows progress status.
7. `OnboardingRunService.startRun` returns a mocked `runId`.
8. UI calls `OnboardingRunService.getRunStatus` for mocked status.
9. If status returns `done`, UI shows the results view.
10. HR user can select `Aprovar plano` to register approval in the current review session without sending communications or triggering downstream actions.
11. HR user can select `Solicitar ajustes`, enter required feedback, and register the requested changes in the current review session.
12. If status returns `error`, UI shows an error banner and keeps form data for correction/retry.
13. HR user can select `Limpar` to return to `idle` with a clean form.

## 7. Finite-State Machine

States:

```ts
export type GeneratePlanState = "idle" | "running" | "done" | "error";
```

Events:

```ts
export type GeneratePlanEvent =
  | { type: "RUN_CLICKED" }
  | { type: "RUN_STARTED"; runId: string }
  | { type: "RUN_DONE"; result: OnboardingPlanResult }
  | { type: "RUN_FAILED"; message: string }
  | { type: "RESET_CLICKED" };
```

Transition table:

| Current state | Event           | Next state | UI effect                                       |
| ------------- | --------------- | ---------- | ----------------------------------------------- |
| `idle`        | `RUN_CLICKED`   | `running`  | Validate form, disable Run, show running banner |
| `running`     | `RUN_STARTED`   | `running`  | Store `runId`, continue progress display        |
| `running`     | `RUN_DONE`      | `done`     | Store result, show results view                 |
| `running`     | `RUN_FAILED`    | `error`    | Show error banner, keep form values             |
| `error`       | `RUN_CLICKED`   | `running`  | Retry with current form values                  |
| `idle`        | `RESET_CLICKED` | `idle`     | Clear form and result                           |
| `error`       | `RESET_CLICKED` | `idle`     | Clear form, error, and result                   |
| `done`        | `RESET_CLICKED` | `idle`     | Clear result and show fresh form                |

Invalid transitions should be ignored or handled as no-ops.

## 9. Service Stubs

Model sketch:

```ts
export interface EmployeeOnboardingInput {
  fullName: string;
  email: string;
  role: string;
  department: string;
  directManager: string;
  startDate: string;
  employmentType: string;
  workMode: string;
  seniority?: string;
  location?: string;
  contractRegion?: string;
  preferredLanguage?: string;
  equipmentNeeds?: string;
  specialAccessNotes?: string;
}

export interface StartRunResponse {
  runId: string;
  status: "running";
}

export interface RunStatusResponse {
  runId: string;
  status: "running" | "done" | "error";
  message: string;
  result?: OnboardingPlanResult;
  errorMessage?: string;
}
```

Service sketch:

```ts
@Injectable({ providedIn: "root" })
export class OnboardingRunService {
  startRun(input: EmployeeOnboardingInput): Observable<StartRunResponse> {
    return of({
      runId: `mock-run-${Date.now()}`,
      status: "running",
    }).pipe(delay(400));
  }

  getRunStatus(runId: string): Observable<RunStatusResponse> {
    return of({
      runId,
      status: "done",
      message: "Plano de onboarding gerado para revisão.",
      result: MOCK_ONBOARDING_PLAN_RESULT,
    }).pipe(delay(900));
  }
}
```

Error simulation may be added behind a development-only toggle or by setting a local constant in the service.

## 11. Status Banner Behavior

Banner text:

| State     | Severity | Text                                                                                 |
| --------- | -------- | ------------------------------------------------------------------------------------ |
| `idle`    | Info     | Pronto para gerar um plano de onboarding.                                            |
| `running` | Info     | Gerando plano de onboarding...                                                       |
| `done`    | Success  | Plano de onboarding gerado para revisao humana.                                      |
| `error`   | Error    | Nao foi possivel gerar o plano de onboarding. Revise o formulario e tente novamente. |

The banner must not imply that communications were sent or access was provisioned. It may indicate approval or requested changes only after the user explicitly selects the matching review action, and should make clear this is session-local until backend persistence exists.

## 12. Results View Requirements

Show these sections:

- Employee profile.
- Executive summary.
- Required documents.
- IT checklist.
- Training path.
- Initial agenda.
- Communications labeled as `Rascunho`.
- Pending actions.
- Risk flags.
- Next recommended actions.

Each communication must be labeled as `Rascunho` and requiring human review.

The results page must keep explicit review actions visible:

- `Aprovar plano` registers local approval for the current review session.
- `Solicitar ajustes` opens a required feedback field and records the requested change in the current review session.
- `Limpar` remains visible as a secondary action so the user can start over.

These review actions must not imply that communications were sent, access was provisioned, or downstream systems were updated.

## 13. Accessibility and UX Rules

- The first route screen must be the usable workbench, not a landing page.
- Theme controls must be keyboard accessible and visibly indicate the selected mode.
- Theme selection must not alter generated plan data or run state.
- Required form fields must expose visible labels and validation messages.
- Validation messages must be programmatically associated with fields where practical.
- `Gerar plano`, `Aprovar plano`, `Solicitar ajustes`, and `Limpar` must be keyboard accessible.
- Running state must be announced visually and through semantic status text.
- Color must not be the only signal for status or risk.
- Results must use semantic headings in a scan-friendly order.

## 14. Error Handling

Frontend validation errors:

- Stay in `idle` or `error`.
- Show field-level messages.
- Do not call `startRun`.

Mock service error:

- Transition to `error`.
- Preserve form values.
- Show a banner-level error message.
- Allow retry by selecting `Gerar plano` again.
- Allow clearing with `Limpar`.

Unexpected missing result:

- Treat as `error`.
- Show a generic message.
- Keep `runId` available in developer logs only if useful.

## 15. Acceptance Criteria

- A user can access the workflow at one route.
- A user can fill the basic employee onboarding form.
- `Gerar plano` is disabled or prevented when required fields are invalid.
- `Gerar plano` transitions the finite-state machine from `idle` to `running`.
- Mock service returns a run id and mocked plan result.
- Successful mocked status transitions the UI to `done`.
- Done state shows all required result sections.
- Done state exposes explicit review actions, not only `Limpar`.
- `Aprovar plano` records a session-local approval and keeps external-action safety copy visible.
- `Solicitar ajustes` requires feedback before recording a session-local change request.
- `Limpar` clears form, result, review decision, feedback, and error state.
- Error state can be reached through mocked failure handling.
- Status banner reflects `idle`, `running`, `done`, and `error`.
- No UI claims that messages were sent, approvals happened, or systems were provisioned.
- User can switch between `Claro` and `Escuro`.
- Theme selection is persisted locally for later visits.
