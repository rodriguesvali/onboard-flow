# Backend Implementation Plan — OnboardFlow AI

Generated by: `@backend.eng`  
Phase: Build  
Date: 2026-05-31  
Status: Approved by Agentic Architect

## 1. Purpose

Implement the OnboardFlow AI backend as a separate Python service aligned with the approved SAD:

- FastAPI API boundary.
- DDD plus Hexagonal Architecture.
- CrewAI Flow plus bounded Crew orchestration.
- Pydantic JSON as the primary contract.
- Markdown as a derived human-readable rendering.
- SQLite MVP persistence managed by Alembic.
- Action history with fixed mock HR user attribution.

This plan supersedes the earlier Markdown-first/local-command-only draft. API, structured JSON, SQLite/Alembic, and refinement are MVP requirements, not future work.

## 2. Runtime And Architecture

Stack:

- Python 3.12.
- `uv` dependency management.
- FastAPI.
- Pydantic v2.
- SQLAlchemy 2.x.
- Alembic.
- SQLite.
- CrewAI.
- pytest.

Backend layers:

- `domain`: onboarding models, statuses, value objects, and validation-friendly contracts.
- `application`: generation, run retrieval, refinement, output normalization, and action-history use cases.
- `ports`: catalog, persistence, Flow orchestration, Markdown rendering, and future model access boundaries.
- `adapters`: FastAPI, local JSON catalogs, SQLite persistence, Markdown rendering, and CrewAI/Flow boundary.
- `config`: environment settings and model-profile defaults.

Dependency rule:

- Domain and application logic must not depend on FastAPI, CrewAI, SQLite, SQLAlchemy, Alembic, or provider SDKs.
- Framework/provider concerns stay in adapters.

## 3. API Contracts

Approved routes:

- `POST /api/onboarding/generate`
- `GET /api/onboarding/runs/{runId}`
- `POST /api/onboarding/runs/{runId}/refine`

Generation request uses the frontend-approved camelCase fields:

- Required: `fullName`, `email`, `role`, `department`, `directManager`, `startDate`, `employmentType`, `workMode`.
- Optional: `seniority`, `location`, `contractRegion`, `preferredLanguage`, `equipmentNeeds`, `specialAccessNotes`.

Generation response:

```json
{
  "runId": "run_...",
  "status": "running"
}
```

Run status response:

- `runId`
- `status`: `running`, `done`, or `error`
- `message`
- `result`
- `markdown`
- `validationResult`
- `agentActivity`
- `errorMessage`

Plan result shape remains compatible with the approved frontend `OnboardingPlanResult`:

- `employeeProfile`
- `executiveSummary`
- `requiredDocuments`
- `itChecklist`
- `trainingPath`
- `initialAgenda`
- `communications`
- `pendingActions`
- `riskFlags`
- `status`
- `nextRecommendedActions`

Refinement request:

```json
{
  "instruction": "Revisar prazos da agenda inicial.",
  "planVersion": 1
}
```

Refinement response returns the new revision id, revision number, validated plan JSON, Markdown, and validation result.

## 4. Flow And Crew Boundary

`OnboardingFlow` owns:

- Run state.
- Required-field validation.
- Draft-mode or error routing.
- Specialist output acceptance.
- Final plan normalization.
- Markdown rendering.
- Persistence and action-history recording.

`OnboardingAnalysisCrew` owns bounded specialist analysis only:

- HR Intake.
- Compliance.
- IT Provisioning.
- Training.
- Communication.

CrewAI rules:

- `agents.yaml` and `tasks.yaml` remain externalized config.
- `Process.sequential` is the MVP execution mode.
- `allow_delegation=False`.
- Every specialist task must return parseable structured JSON.
- Communication runs only after profile, compliance, IT, and training outputs are available.
- Agents do not persist data, approve plans, send communications, or provision access.

Model profiles:

- `default`
- `reasoning`
- `efficient`
- `creative`
- `tool_calling`
- `refinement`

All profiles initially resolve to `gemini-3.5-flash`.

## 5. Persistence And Audit

SQLite is the MVP persistence layer.

Alembic is the source of truth for schema changes.

Persist:

- Runs.
- Generated plans.
- Plan revisions.
- Action history.
- Validation results.
- Rendered Markdown.

Every generation, validation, specialist task, normalization, refinement, retry, and error path records action history with:

- Fixed mock HR user.
- Task id when relevant.
- Agent name when relevant.
- Model provider/model/profile when relevant.
- Validation result.

## 6. Implementation Sequence

1. Verify mandatory docs/tooling through Context7 before coding.
2. Scaffold `backend/` with Python package, settings, pyproject, README, `.env.example`, and local catalogs.
3. Implement domain and application contracts.
4. Implement SQLite persistence with Alembic migration.
5. Implement deterministic local Flow/Crew boundary for MVP tests and demos.
6. Add CrewAI YAML config for agents and tasks.
7. Implement FastAPI routes and DI.
8. Add tests for generation, run retrieval, invalid input, refinement, aliases, persistence, and schema compatibility.
9. Document build evidence in `project-context/2.build/backend.md`.

## 7. Acceptance Criteria

- `uv sync --all-extras --dev` succeeds.
- `uv run alembic upgrade head` succeeds.
- `uv run pytest` succeeds.
- API returns frontend-compatible JSON.
- Markdown is generated from validated JSON.
- SQLite persists run state and action history.
- Refinement creates a new revision and preserves plan schema.
- No generated output claims that messages were sent, access was provisioned, or plans were externally approved.

## 8. Known Boundaries

- Real Gemini calls are not required for tests; model access is represented by settings and model-profile logging.
- Real HRIS, ITSM, IAM, LMS, email, chat, payroll, SSO/RBAC, and analytics integrations remain out of scope.
- Backend-persisted approval is not part of this gate; frontend approval remains session-local until a later approved integration step.
- `project-context/2.build/setup.md` is still absent and is recorded as a Build-preparation dependency.
